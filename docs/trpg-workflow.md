# TRPG 工程说明

## 与主应用的边界

- 复用 `user`、`user_info`、Auth.js `account` / `session`、`stores`、`tables` 及会员余额数据。
- `libs/db/src/trpgSchema.ts` 定义跑团场次、报名和门店授权。Drizzle Kit 同时读取此文件；主应用自动生成的通用 GraphQL CRUD 不包含这三张表，避免绕过审核和席位约束。
- 自定义 GraphQL schema/resolvers 沿用现有 `schema.graphql`、`resolvers/_all.ts`、guards/errors/validation 模式。数据访问在 `server/services/trpg`；简单查询使用 Drizzle builder，容量和排期约束使用参数化单条 SQL。
- 旧活动、公众号 AI、推荐、搜索和 OG 卡片无需新增跑团过滤。两种业务不会共用一个报名状态字段。
- 后台使用项目已有 DataTable、daisyUI/Tailwind 主题和 i18n。GraphQL operations 位于既有 operations 目录，通过 `codegen:trpg` 生成独立的类型和 hooks；不手工修改生成文件。
- HTTP GraphQL 入口把执行器的文本错误转换为规范的 `{message}` 对象，保证 Apollo 能显示服务端错误。微信 AI 内部调用保留原有返回格式。

## 权限与流程

管理员可以管理全部门店。店员必须同时具有 `user.role=staff` 和对应 `trpg_access.staff` 授权；主持人需要 `trpg_access.host`。所有写入从数据库重新读取账号状态和权限，不信任客户端传入的角色。

主持人提交后进入待审；有门店审核权限的人可直接发布或代指定合法主持人。退回后仅本人或对应门店审核员可修改再提交。审核、改期和状态转换带 revision，旧页面提交会被拒绝。

发布/定档在同一条数据库写入内核对桌位容量、所属门店及主持人跨店时间冲突。报名使用 `INSERT … SELECT` 同时校验容量并占位；部分唯一索引避免同一玩家重复有效报名。确认定金只是人工核验记录，不执行扣款。拒绝或取消释放席位。

时间待定场次可先登记意向。定档后意向玩家享有最长 24 小时优先期，并在报名截止前至少留出 1 小时；缺少足够优先时间时拒绝定档。页面时间明确使用北京时间，接口使用带时区的 ISO 字符串。

主持人只能读取自己场次的名单，并且不会收到手机号。审核员只能读取授权门店的名单和会员记录。列表与名单均分页，避免长期使用后被 GraphQL 的数组上限截断。

微信小程序先换取 openid，再用微信服务端返回的已验证手机号关联已有会员。客户端不能直接指定会员 ID。小程序令牌仅保存 SHA-256 摘要，7 天到期，退出后删除；账号停用时立即失效。现有手机号合并流程调用独立的事务性合并助手，保留更强的报名状态并撤销旧账号令牌。

## 数据库迁移

本分支面向主分支尚未应用旧 PR 迁移的数据库，新增 `0056_trpg_workflow.sql`，仅创建三张独立表及索引，不改写旧活动或会员表。

**如果某个测试环境曾执行旧 PR #4/#5 的同名迁移，不能把新文件当作已升级完成。** Wrangler 会按迁移名记录状态。请先确认该环境的数据保留要求，在隔离测试数据库重建验证，或者另行编写有数据映射的向前迁移；本分支不自动删除或猜测迁移已有数据。未对远程 D1 执行任何迁移。

通过既有部署流程先在隔离 D1 应用迁移并配置 Worker 微信 secrets，再部署对应 Worker。管理员从工作台的门店权限表单授予主持/审核权限。权限保存会替换当前门店的权限，未勾选的权限会被撤销。

## 验证与限制

自动化覆盖真实 SQLite 上的容量、幂等、排期、权限、意向转报名、定金审核、账户合并；GraphQL schema/权限；微信身份关联、令牌摘要/失效；小程序 operations 校验与过期登录/错误处理。后台使用模拟 GraphQL 数据做浏览器交互与响应式检查；截图不入库。

本次实现仍是跑团工作流，不包含积分商城、商品上传、时间卡、公会信箱、独立模组库或在线支付。未部署生产环境。真实微信授权与图片域名仍需配置后的真机验收。

全仓 `tsc --noEmit` 当前不能通过；主分支副本同样存在 Worker 环境类型、旧页面和依赖声明等诊断。本次不将全仓类型检查标记为通过，也不混入无关的批量修复。
