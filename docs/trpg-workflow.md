# TRPG 工程说明

## 与主应用的边界

- 复用 `user`、`user_info`、Auth.js `account` / `session`、`stores`、`tables` 及会员余额数据。
- `libs/db/src/trpgSchema.ts` 定义跑团场次、报名和门店授权。Drizzle Kit 同时读取此文件；主应用自动生成的通用 GraphQL CRUD 不包含这三张表，避免绕过审核和席位约束。
- 自定义 GraphQL schema/resolvers 沿用现有 `schema.graphql`、`resolvers/_all.ts`、guards/errors/validation 模式。数据访问在 `server/services/trpg`；简单查询使用 Drizzle builder，容量和排期约束使用参数化单条 SQL。
- 旧活动、公众号 AI、推荐、搜索和 OG 卡片无需新增跑团过滤。两种业务不会共用一个报名状态字段。
- 后台使用项目已有 DataTable、daisyUI/Tailwind 主题和 i18n。GraphQL operations 位于既有 operations 目录，通过 `codegen:trpg` 生成独立的类型和 hooks；不手工修改生成文件。
- HTTP GraphQL 入口把执行器的文本错误转换为规范的 `{message}` 对象，保证 Apollo 能显示服务端错误。微信 AI 内部调用保留原有返回格式。

## 权限与流程

管理员可以管理全部门店。账号身份固定为五种：顾客 `customer`、会员 `member`、主持人 `host`、店长 `staff`、管理员 `admin`。会员身份在会员管理中授予（仅顾客可升级，主持人/店长/管理员优先）；主持人身份由主持授权自动同步，撤销最后一个主持授权时按有效时长卡回落为会员或顾客。店长必须同时具有 `user.role=staff` 和对应 `trpg_access.staff` 授权；主持人身份两店共用：任一 `trpg_access.host` 授权表示可在两店主持，店长审核权限仍按门店保存。所有写入从数据库重新读取账号状态和权限，不信任客户端传入的角色。

主持人提交后进入待审；有门店审核权限的人可直接发布或代指定合法主持人。退回后仅本人或对应门店审核员可修改再提交。审核、改期和状态转换带 revision，旧页面提交会被拒绝。

地点待定：`trpg_sessions.store_id` 可为空。主持人只要有任意门店的主持权限即可发布，不选择门店；场次进入待审核，管理员或任一店长可审核。公开场次列表在任意门店筛选下都会带出地点待定场次，门店名显示“地点待定”。人齐后由主持人（或审核员）在确定排期时选择门店、包间和时间，`store_id` 落库并直接生效，不重新审核；已有意向玩家仍保留优先确认时间。后台约团排期的“新建地点待定场次”可直接创建，管理员或店长创建后即为已发布；确定门店与包间在小程序场次管理中完成。

发布/定档在同一条数据库写入内核对桌位容量、所属门店及主持人跨店时间冲突。报名使用 `INSERT … SELECT` 同时校验容量并占位；部分唯一索引避免同一玩家重复有效报名。确认定金只是人工核验记录，不执行扣款。拒绝或取消释放席位。

时间待定场次可先登记意向。定档后意向玩家享有最长 24 小时优先期，并在报名截止前至少留出 1 小时；缺少足够优先时间时拒绝定档。页面时间明确使用北京时间，接口使用带时区的 ISO 字符串。

主持人只能读取自己场次的名单，并且不会收到手机号。审核员只能读取授权门店的报名名单；有会员管理权限的管理员及店长使用两店共用的会员目录和已完成跑团记录。列表与名单均分页，避免长期使用后被 GraphQL 的数组上限截断。

微信小程序先换取 openid，再用微信服务端返回的已验证手机号关联已有会员。客户端不能直接指定会员 ID。小程序令牌仅保存 SHA-256 摘要，7 天到期，退出后删除；账号停用时立即失效。现有手机号合并流程调用独立的事务性合并助手，保留更强的报名状态并撤销旧账号令牌。

## 数据库迁移

本分支面向主分支尚未应用旧 PR 迁移的数据库，新增 `0056_trpg_workflow.sql`，仅创建三张独立表及索引，不改写旧活动或会员表。`0060_trpg_location_tbd.sql` 因需要把 `store_id` 改为可空并放宽“已排期必须有包间”的约束，会同时重建 `trpg_sessions` 和引用它的 `trpg_registrations`；执行前必须备份，并按迁移文件顺序应用。

**如果某个测试环境曾执行旧 PR #4/#5 的同名迁移，不能把新文件当作已升级完成。** Wrangler 会按迁移名记录状态。请先确认该环境的数据保留要求，在隔离测试数据库重建验证，或者另行编写有数据映射的向前迁移；本分支不自动删除或猜测迁移已有数据。未对远程 D1 执行任何迁移。

通过既有部署流程先在隔离 D1 应用迁移并配置 Worker 微信 secrets，再部署对应 Worker。管理员从主持人管理页面搜索会员并授予两店通用主持身份；授予与撤销主持身份均保留各门店已有的店员审核权限。既有场次不会自动取消，撤销权限时需要检查后续排期。

## 后台运营入口

- `/dash/trpg`：默认按北京时间显示周排期，支持上一周、下一周、日期跳转和门店筛选；跨日场次显示在所覆盖的日期。每批 30 条，可继续加载完整周排期。待审核、时间待定和全部场次分别提供分页列表。点开场次复用既有审核、改期和报名处理流程。
- `/dash/trpg-hosts`：独立的主持人管理页面，使用两店共用名册，不提供门店筛选。管理员可搜索已有会员、确认授权或撤销；店员只读。主持身份两店通用，重复的门店授权记录在目录中只出现一次。系统管理员本身的全局权限不作为主持身份列出。
- `/dash/trpg-members`：独立的会员管理页面，使用两店共用的会员名册，不提供门店筛选。展示积分、储值余额和两店已完成跑团记录；管理员可打开既有账号与会员卡详情页；主持身份的调整统一在主持人管理页面操作。
- 新目录接口 `trpgDirectory` 只允许管理员或拥有审核授权的店员使用，服务端重新读取权限，按昵称和账号 ID 稳定排序分页。主持人不能通过此接口读取会员资料。

主持身份通过 `setTrpgHost` 原子更新，保留各门店的 `staff` 字段；查询按账号去重。`trpgDirectory` 与 `trpgMemberHistory` 的旧 `storeId` 参数仅为兼容保留，不再分隔会员资料。

这些入口复用现有表，无额外数据库迁移。界面没有把积分或余额变成独立的新账本，也不新增支付或扣款流程。

## 验证与限制

自动化覆盖真实 SQLite 上的容量、幂等、排期、权限、意向转报名、定金审核、账户合并；GraphQL schema/权限；微信身份关联、令牌摘要/失效；小程序 operations 校验与过期登录/错误处理。后台使用模拟 GraphQL 数据做浏览器交互与响应式检查；截图不入库。

2026-11-15 已补充积分商城、商品 HTTPS 封面、公会信箱和回复、积分扣减及兑换券核销，见 trpg-release-20261115.md。独立时间卡、模组库和在线支付仍不在此次迁移范围。未部署生产环境；真实微信授权与图片域名仍需配置后的真机验收。

全仓 `tsc --noEmit` 当前不能通过；主分支副本同样存在 Worker 环境类型、旧页面和依赖声明等诊断。本次不将全仓类型检查标记为通过，也不混入无关的批量修复。

### 团类型与收费

运行 0056 后应用 0057_trpg_session_type.sql。旧场次默认标记为商团，原 fee_cents 保留用于历史兼容；新建/重新提交按 sessionType 规范化，客户端不得以 feeCents 为 0 判断免费。商团为每人 118 元 / 5 小时；俱乐部团按当日桌游门票；测试团会员免费，其他客人按当日门票。门票工作日 40 元 / 人，周末及法定节假日 60 元 / 人。

当前展示收费规则，不根据星期推算法定假期，不自动判定会员免单或扣款。非商团 feeCents 为 0 表示无固定团费，不代表无需门票；原固定团费定金提示只用于商团。

### 周排期图片导出

周排期日期栏的“导出排期图片”按当前周、门店重新读取完整分页并下载 PNG，包含现有品牌 SVG Logo、北京时间、场次状态、主持人、场地、席位和收费规则。与后台周视图一致，跨日场次在涉及日期重复展示；未审核及已取消等状态明确标注。导出不包含报名人员名单和联系方式，不写入媒体库。图片高度超出浏览器安全范围时提示按具体门店导出，不静默截断。
