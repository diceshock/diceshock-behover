# 前端代码检查与改进计划 · 2026-11-20

> 检查范围：`apps/diceshock/src/client` + `apps/diceshock/src/apps`（177 个文件 / 42248 行，不含 `__generated__`）。
> 方法：结构盘点 + 模式扫描 + 关键页面抽样阅读。

---

## 摘要

前端**有不错的基建**（统一的筛选 hook、消息提示、原子状态、DashTable 封装、可测试的纯函数），但存在四类结构性问题：

1. **超大页面**：单个文件 2000 行，改一处要翻半天
2. **数据层不统一**：35 处手工 `client.query`，缓存策略各页面自己定
3. **类型安全靠断言**：379 处 `as`、48 处 `any`
4. **权限判断散落**：角色规则硬编码在 4 个地方

这些不是"坏代码"，而是**随着功能堆叠形成的债**，会在加功能时越来越慢。

## 二、问题清单（按优先级）

### P0｜正确性与安全

**1. 前端权限判断散落且硬编码**

位置：`DashNavMenu.tsx:78`、`users.tsx:189`、`users.tsx:363`、`users.tsx:431`

现状：每个地方自己写 `role === "admin" || role === "staff"`。
风险：角色规则一变（比如加入 `host`），要逐个改，漏一处就是越权或误拦。
建议：抽一个 `usePermission()` / `can(action)` 统一判断，规则集中在一处（可与后端 `DASH_ROLES` 对齐）。

**2. "后端有、前端漏"的接口**

实例：`setUserPassword` 后端早在 `resolvers/auth.ts:711` 就有（仅管理员），但前端从没调用入口，导致「管理员不能给店员设密码」被当成 bug。
建议：加一个**接口清单核对**（GraphQL schema 里的 mutation vs 前端 `dash-*.graphql` 里的操作），缺失项每月对一次。

**3. 登录态与账号绑定混乱（跨端）**

实例：`Gahon` 有 3 个用户记录，网页微信登录会进另一个号（详见开发计划文档）。
前端影响：登录后角色/数据不一致，用户以为"登错号"。
建议：见 `dev-plan-2026-11-20.md` 任务 2、3。

### P1｜可维护性（影响开发速度）

**4. 超大页面**

| 文件 | 行数 | 问题 |
|---|---|---|
| `users_.$id.tsx` | 2029 | 用户详情 + 会员卡 + 点位 + 密码 + 通知，5 类功能挤在一个文件 |
| `orders_.settle.tsx` | ~1800 | 结算流程 + 明细 + 弹窗 |
| `tables_.$id.tsx` | ~1500 | 桌台详情 + 订单 + 操作 |

风险：改一个卡片要滚动很久；多人同时改容易冲突；单测难写。
建议：按 Tab 拆成子组件（`<BasicTab />`、`<MembershipTab />`、`<OccupancyTab />`），每个子组件独立文件；页面只负责路由与数据下发。

**5. 数据层不统一**

现状：
- 0 处用 Apollo hooks，35 处手工 `client.query`，于是每个页面自己写 loading / error / refetch
- 缓存策略各处不同：`network-only`（多）、`cache-and-network`（少数）
- 没有统一的"查询 + 三态 + 重试"封装

风险：同一个数据在不同页面表现不一致（有的闪、有的用缓存、有的报错不提示）。
建议：抽 `useDashQuery(document, variables, options)` 统一处理 loading/error/refetch，并约定默认 `fetchPolicy`。

**6. 类型安全靠断言**

379 处 `as` + 48 处 `any`。大部分是 GraphQL 返回值到本地类型的转换（如 `MembershipPlan`）。
风险：后端字段一变，前端不报错、运行时才炸。
建议：
- 优先用 codegen 生成的类型直接透传，减少中间层转换
- 对确实需要的转换，写成带校验的 `parseXxx()` 纯函数（可单测）
- 分批把 `any` 清零（`noExplicitAny` 已是 error，但存在历史豁免）

---

### P2｜体验与工程质量

**7. 硬编码 URL（28 处）**

外部链接、微信菜单地址等散落在组件里，改域名要全局搜。
建议：集中到 `shared/config.ts`（或环境变量），组件只引用常量。

**8. 重复的 loading / error 三态**

4 个页面手工维护 `const [loading, ...]` / `const [error, ...]`。
建议：与 P1-5 一起解决（统一查询 hook）。

**9. 错误边界覆盖不足**

只有 3 处 `ErrorBoundary`，页面级崩溃会影响整个后台。
建议：在 `dash.tsx` 路由层加一个兜底，单个 Tab 加局部边界。

**10. 测试覆盖**

已有 `tests/` 目录且部分纯函数有单测（`buildFilter`），但页面级测试少。
建议：新拆出的 hooks 与纯函数必须带测试（成本低、收益高），页面交互测试按需补。

## 三、改进计划

### 第一批｜正确性（1-2 天）

| 事项 | 产出 | 工作量 |
|---|---|---|
| 统一权限判断 | `usePermission` + 替换 4 处硬编码 | 半天 |
| 接口清单核对 | 一份 schema ↔ 前端操作的差异清单，补齐缺失入口 | 半天 |
| 登录绑定修复 | 按 `dev-plan-2026-11-20.md` 任务 1/2 | 1 天（含数据迁移） |

**验收**：角色变更只改一处；后台所有管理员该有的操作都有入口；三种登录方式进同一个号。

### 第二批｜拆分大页面（3-5 天）

| 文件 | 拆法 | 工作量 |
|---|---|---|
| `users_.$id.tsx` | 按 Tab 拆 3-5 个子组件 + 一个 `useUserDetail` 数据 hook | 2 天 |
| `orders_.settle.tsx` | 拆结算表单、明细表、弹窗 | 1.5 天 |
| `tables_.$id.tsx` | 拆桌台信息、订单列表、操作区 | 1 天 |

**验收**：单文件不超过 500 行；原有功能回归通过。

### 第三批｜数据层统一（约 1 周）

1. 抽 `useDashQuery` / `useDashMutation`（三态 + 重试 + 统一提示）
2. 约定默认缓存策略（列表 `cache-and-network`，详情 `network-only`）
3. 迁移 35 处手工 `client.query`，按页面逐个替换
4. 同步清理重复的 loading/error state

**验收**：`client.query` 直接调用归零；所有页面错误提示一致；重复请求减少。

### 第四批｜类型与配置（持续）

1. `as` 断言分批改为校验函数（每批次 ≤ 20 处，带测试）
2. `any` 清零（历史豁免一并处理）
3. 硬编码 URL 收敛到配置
4. 路由级 ErrorBoundary

**验收**：`biome` 无豁免项；`any` 为 0；域名变更只改一处。

## 五、建议的推进方式

- **第一批立刻做**：成本低、直接影响"能不能用"
- **第二批按需做**：下次要改那个页面时，先拆再加功能（避免拆完又堆回去）
- **第三批排期做**：需要一次性投入，但收益最大（后续所有页面都受益）
- **第四批持续做**：不单独排期，跟着改动走
